# ADR-002: Use zod for runtime schema validation

## Status

Accepted

## Context

The codebase had 12 unsafe `as` type assertions when parsing JSON config files. Stack manifests, base configs, and OMO configs were all trusted without validation. A malformed manifest would crash at runtime with an unhelpful error, or worse, silently produce wrong behavior. There was no validation at the boundary between disk and code.

## Decision

Use zod (v4.4.3) schemas to validate all parsed JSON at runtime, replacing `as` assertions with `.parse()` calls.

## Rationale

Zod gives us both runtime validation and type inference from a single schema definition. One `StackManifestSchema.parse(data)` call replaces `JSON.parse(data) as StackManifest` and adds real checking. Parse failures produce structured error messages that tell you which field is wrong and why. The inferred types (`z.infer<typeof Schema>`) stay in sync with the schemas automatically, so the type and the validation can never drift apart. We use `.passthrough()` on schemas that need forward compatibility with unknown keys from future manifest versions.

## Consequences

Adds ~50KB to dependencies. Schemas must be maintained alongside the code that uses them, but since types are inferred, there's only one source of truth. The `.passthrough()` lenient mode means unknown keys pass through silently, which is intentional for forward compatibility but could hide typos in new fields.
